# Ключевые решения (ADR)

Формат: `## ADR-NNN — заголовок` → решение и почему. Меняется, когда меняется контекст.

## ADR-001 — Ядро как фреймворк, бой как отдельный проект

**Решение**: `Sektor.TurnBased.Core` (+`Core.Abstractions`) не знает про конкретную игру; `Sektor.TurnBased.Battle` — первый потребитель ядра.

**Почему**: уроки прошлых проектов (EpicSeven-клоны, Disciples.Net, Hearthstone-клоны) — код обрастает играми-зависимостями и превращается в «ваниль». Играем от фреймворка: вторая мини-игра на ядре докажет переносимость (см. roadmap).

## ADR-002 — Умеренное упрощение, без позиций и гексов

**Решение**: бой — абстрактный список команд с целями; позиции/клетки не закладываются.

**Почему**: YAGNI. Для проверки ядра и основ боя пространственность не нужна; добавится позже, если понадобится. Статы/эффекты/правила/фазы остаются пригодными для расширения.

## ADR-003 — Данные-ресурсы вместо enum-статов

**Решение**: статы и статусы — данные (`StatDefinition`, `StatusDefinition`) по строковым Id, а не enum; `ResourceContainer` держит значения.

**Почему**: в EpicSeven-клоне `StatType` enum плодил switch по всей базе и делал добавление стата правкой многих файлов. Данные — это OCP: новый стат = новое определение, ноль правок старого кода.

## ADR-004 — Эффекты = процессинг, митигация — флэт-редукция

**Решение**: урон/лечение/модификации/статусы/призыв — полиморфные эффекты по цепочке; митигация урона — плоская (например, вычитание защиты), без стадий типа «armor → resist → block».

**Почему**: стадийность (как в Disciples.Net) оказалась громоздкой и легко ломалась порядком применения. Флэт-модель проще и читается сверху вниз; при необходимости этапы добавляются как отдельные эффекты.

## ADR-005 — Строковые Id + валидация на загрузке

**Решение**: всё по строкам (`BattlePhaseIds`, `ContentRegistry.TryGet`, `EventType`), ошибки ссылок ловит `ContentValidator` при `BattleEngine.Create`.

**Почему**: нет дихотомии «enum в коде vs id в данных»; опечатки валятся на старте, а не в бою. Тесты на валидатор закрепляют это.

## ADR-006 — Шина событий в v1: Before/After + applyBase

**Решение**: `GameEventBus.Raise(evt, applyBase)` с хуками до/после базовой логики; подписчики изолированы try/catch; в визуал уходит отдельная очередь снимков.

**Почему**: простое и достаточное событийное связывание без внешних библиотек. Разделение «доменная логика» и «визуальные снимки» снимает классическую проблему каскадов и «UI внутри домена».

## ADR-007 — AI по оценке урона

**Решение**: `BattleAi` выбирает действие по `EstimateDamage` (пре-коммит, без побочных эффектов), бьёт по слабейшей цели; при равном уроне — слабее цель.

**Почему**: детерминизм и простота. Модель «клик-цель» (как в Disciples.Net) без стратегической глубины не требует дерева поиска. Расширение — дополнительные стратегии выбора.

## ADR-008 — Вторая мини-игра как критерий готовности ядра

**Решение**: до активного развития боя сделана вторая игра на ядре — фазовый диалог/квест (`src/Dialog`).

**Почему**: только так проверяется, что ядро действительно фреймворк, а не «спец-библиотека Battle». Диалог принципиально отличается от боя (нет статов/акторов), но использует те же `GamePipeline`, `GameEventBus`, `VisualQueue`, `ContentRegistry`; заодно впервые задействованы вложенные пайплайны (`CreateChildPipeline`) — «диалог внутри диалога». Итог: ADR выполнен, ядро переносимо.
