# Архитектура ядра

Минимальный фреймворк для пошаговых игр: пайплайн фаз, шина событий, очередь визуальных событий, детерминированный RNG, каталог контента. Без привязки к конкретной игре.

## Пайплайн фаз (`GamePipeline`)

Фазы — единица логики, которая что-то делает и возвращает переход. Игра собирается из фаз в пайплайн.

- `Register(phase)` — зарегистрировать фазу до запуска (повторный Id — ошибка).
- `Start(phaseId)` — запустить с фазы (вызывает `OnEnter`).
- `Advance()` — выполнить один шаг: продвинуть активного дочернего пайплайна или текущую фазу.
- `Resume()` — повторно выполнить текущую фазу (продолжение после события/команды).
- `JumpTo(phaseId)` — переход с `OnExit` текущей и `OnEnter` целевой.
- `ProcessCommand(command)` — отдать команду активной (подвешенной) фазе или дочернему пайплайну.
- `CreateChildPipeline()` — вложенный пайплайн (бой внутри рейда, рейд внутри недели).
- `Stop()` — остановить всё, включая дочерние.

**Инвариант**: пайплайн никогда не бросает исключений; все ошибки — `Result`.

## Переходы (`PhaseTransition`)

Фаза завершает своё выполнение одним из четырех вариантов:

- `Next(phaseId)` — перейти к фазе.
- `Suspend(reason)` — подождать ввода (пайплайн «замер» до команды/события).
- `Resume()` — продолжить выполнение текущей фазы после команды.
- `Finish()` — завершить пайплайн.

Это позволяет писать фазы декларативно, а всю механикой перехода держать в ядре.

## Жизненный цикл фазы (`IGamePhase`)

- `Bind(pipeline)` — получить ссылку на пайплайн (для создания дочерних).
- `OnEnter(context)` — вход в фазу.
- `Execute(context)` — основной шаг, возвращает `PhaseTransition`.
- `OnExit(context)` — выход из фазы.
- `OnCommand(context, command)` — обработка команды, возвращает `Result<PhaseTransition?>` (null — команда не меняет поток).

## Контекст игры (`GameContext`)

Держит доступные всем фазам сервисы: `Rng` (детерминированный), `Content` (каталог), `Events` (шина), `Visuals` (очередь), `Log` (текстовый лог). Создаётся один на игру и передаётся фазам.

## События (`GameEventBus`)

Шина доменных событий с хуками `Before`/`After`:

- `Raise<TEvent>(evt, applyBase)` — вызывает `Before`-хуки (могут отменить событие через `IsCancelled`), затем базовую логику `applyBase`, затем `After`-хуки.
- Ошибки подписчиков изолируются (try/catch) — не рушат игру.

Используется для связи внутри логики. Визуализация идёт **отдельным** каналом — `VisualQueue`.

## Визуальные события (`VisualQueue`, `VisualEvent`)

- Ядро **мгновенно** меняет состояние и добавляет `VisualEvent` (снимок: строковый `EventType`, `SourceRuntimeId`, `TargetRuntimeId`, `Value`, `Payload`) в FIFO-очередь.
- UI последовательно считывает очередь и анимирует. Так мгновенная логика отделена от плавной отрисовки, и ядро не знает про UI.
- `EventType` — строка («Damage», «Heal», «StatusApply», «Shake», …), а не enum.

## Лог (`GameLog`)

Текстовый журнал происходящего для отладки и replay. Детерминирован при том же seed.

## Каталог контента (`ContentRegistry`)

Реестр данных по строковым Id: `Content.TryGet<T>(id, out value)`. Всё, что можно сломать на старте, валидируется при загрузке (см. `ContentValidator` в Battle).

## Детерминированный RNG (`DeterministicRng`)

Вся случайность идёт через него; seed задаётся при создании `GameContext`. Одинаковый seed → одинаковый лог, события и исход боя. Основа для тестов и реплеев.
